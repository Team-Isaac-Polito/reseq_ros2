# reseq_traction_autonomy

Autonomous driving for Rese.Q's traction, tested in Gazebo. A task manager takes goals from MCP tools or a local HTTP API and lets Nav2 drive to them. A goal is either a pose on the map or an instruction for a visual navigation model, which then proposes short subgoals.

A command passes through these steps, in order:

1. MCP tools or the HTTP API
2. Task manager
3. Navigation model (visual tasks only)
4. Nav2
5. Gate
6. `cmd_vel_mux`
7. Traction controllers

The manager's gate is the only publisher on `/cmd_vel_nav`, so every Nav2 command still passes through the existing mux and traction controllers. The arm is not touched.

## Build

From the workspace root:

```bash
source /opt/ros/jazzy/setup.bash
colcon build --packages-select reseq_traction_autonomy
source install/setup.bash

python3 -m venv --system-site-packages "$HOME/.venvs/reseq-traction"
"$HOME/.venvs/reseq-traction/bin/pip" install -r src/reseq_traction_autonomy/requirements-mcp.txt
```

After changing the code, rebuild and restart the launch, or the old code keeps running.

## Run in Gazebo

```bash
ros2 launch reseq_traction_autonomy gazebo.launch.py \
  manager_python:="$HOME/.venvs/reseq-traction/bin/python"
```

This starts the world, the robot and app stack, SLAM, Nav2 and the manager. It leaves out the old `autonomy_coordinator`.

Pick a world with `world:=`:

| World | What it is |
|---|---|
| `simple_course.world` (default) | A small room for quick checks. |
| `lane.world` | One RoboCup Rescue mobility lane: 2.4 m wide, 4.8 m long, a bay at each end and a QR code on the end wall. |
| `rescue_maze.world` | A 12 by 8 m search maze with four rooms, hazmat signs, a victim doll and other objects. |

The lane and the maze are generated by `worlds/generate_lane.py` and `worlds/generate_rescue_maze.py`. Change the layout there and rerun the script; it rewrites the world and its textures. Both worlds have an overhead camera on `/overview/image` for recordings.

Gazebo runs as a server and its window is a separate process. Closing the window leaves the simulation running; reopen it with `gz sim -g`, or start without it using `gui:=false`.

## Tools

```bash
ros2 run reseq_traction_autonomy traction_tool get_state
ros2 run reseq_traction_autonomy traction_tool observe
ros2 run reseq_traction_autonomy traction_tool navigate_to_pose \
  '{"x": 0.5, "y": 0.0, "frame": "map", "timeout_s": 30}'
ros2 run reseq_traction_autonomy traction_tool get_task '{"task_id": "TASK_ID"}'
ros2 run reseq_traction_autonomy traction_tool cancel_task '{"task_id": "TASK_ID"}'
ros2 run reseq_traction_autonomy traction_tool stop
```

`traction_tool` posts JSON to `http://127.0.0.1:8765/tools/TOOL_NAME`. The API only listens on localhost; forward port 8765 over SSH for remote use.

For an MCP client, run `bash src/reseq_traction_autonomy/scripts/run_mcp.sh`. It exposes the same seven tools (the six above and `start_visual_navigation`) with a `traction.` prefix.

`navigate_to_pose` also takes `zone_qr`. The task then succeeds only if the camera reads that QR text after arriving. This needs the `computer_vision` detector, which does not run in this simulation.

## Evaluate against ground truth

`traction_eval` runs a course of tasks and measures each leg with Gazebo's true robot pose, not with SLAM:

```bash
ros2 run reseq_traction_autonomy traction_eval            # config/simple_course.yaml
ros2 run reseq_traction_autonomy traction_eval config/lane_course.yaml --repeat 3
ros2 run reseq_traction_autonomy traction_eval my_course.yaml --legs forward
```

For each leg it reports the true distance to the goal, the SLAM estimate of that distance, SLAM drift, path length and time. Results, including the true trajectory, are saved as JSON under `~/.local/state/reseq/traction/eval/`.

A course file lists legs with a goal in the map frame. Visual legs also take `kind: visual`, `instruction` and `model`; their goal is only used for measuring, and the model never sees it.

### Mobility lane

`config/lane_course.yaml` is one lane round trip in `lane.world`: drive down range to the end bay, then return to the start bay. The lane is too narrow for a 1.3 m robot to turn around, so it returns in reverse.

## Driving in reverse

Nav2 may reverse, and it does so when the goal is behind the robot. The FTL controller then makes the tail the leader and applies the turn command to the tail. Nav2 computes that turn for `base_link`, the front module, which now comes last, so its steering arrives one body length too late and the robot swings wider on every leg.

For reverse commands the manager therefore keeps Nav2's speed and replaces the turn. It steers the tail along the straight line through the goal in the direction of the goal's yaw, aiming `reverse_lookahead_m` (0.6 m) ahead. So for a goal behind the robot, set `yaw` to the heading the robot should keep while backing up. If the tail points more than 60 degrees away from that line, Nav2's own turn is used.

## Navigation models

No weights ship with this package. If a model server is missing, the task fails with an error.

### LightNav-0

Start the [LightNav server](https://github.com/lightorigins/LightNav-0/blob/main/docs/DEPLOYMENT.md) on the GPU machine, forward its port, and pass the URL at launch:

```bash
ros2 launch reseq_traction_autonomy gazebo.launch.py \
  manager_python:="$HOME/.venvs/reseq-traction/bin/python" \
  lightnav_url:=ws://127.0.0.1:8050
```

Then call `start_visual_navigation` with `instruction` and `"model": "lightnav"`. Each task opens a fresh LightNav session.

- The manager streams a camera frame every `frame_period_s` (0.25 s, the spacing the model was trained on) and asks for a prediction every `model_period_s` (1 s).
- A prediction is a short list of `[forward, lateral, yaw]` poses relative to where the robot was when the image was taken. The manager sends the farthest reachable one, at most `max_subgoal_distance_m` away, to Nav2.
- A newer prediction replaces the Nav2 subgoal after `subgoal_refresh_s` (3 s), so the model stays in charge.
- If no pose is reachable, for example when the model only turns in place, the prediction is skipped. After `escape_after_unreachable` (2) skipped predictions or failed subgoals, the robot backs up `backup_distance_m` (0.3 m) and the model looks again. A failed subgoal does not end the task.
- LightNav's `stop` flag sometimes appears for a single frame. The task ends only after `stop_confirmations` (3) stops in a row, reported as "Model stop claim; destination not measured".

### Foresight

Build `amrl_msgs` and `legged_deployment` from [foresight_public](https://github.com/ut-amrl/foresight_public) and set these planner parameters:

| Parameter | Value |
|---|---|
| `image_topic` | `/traction/camera/image/compressed` |
| `pose_topic` | `/odometry/filtered` |
| `path_frame_id` | `odom` |

The manager calls `/legged_deployment/foresight_planner`. It rejects paths not in `odom`, paths planned from an image older than `prediction_max_age_s`, and plans the critic rejected. The planner keeps its own image history and has no reset, so restart it between evaluation runs.

### Evaluation goal

Foresight never says it has arrived. For evaluation, `start_visual_navigation` on the HTTP API also accepts `goal_x`, `goal_y`, `goal_frame` and `goal_tolerance`. The model never sees them. The task succeeds when the SLAM pose enters that circle, and a LightNav stop outside it fails the task.

Model pages: [LightNav-0](https://huggingface.co/LightOriginsHQ/LightNav-0), [Foresight VLM](https://huggingface.co/ut-amrl/foresight-qwen3vl-2b-sft), [Foresight grounding policy](https://huggingface.co/ut-amrl/foresight-waypoint-policy).

## How a task runs

- One task runs at a time. Starting a second one fails until the first ends.
- Nav2's output goes to `/traction/nav2/candidate`. The gate forwards it to `/cmd_vel_nav` only while the task has an accepted Nav2 goal, a recent Nav2 command and, for visual tasks, a recent model answer.
- The traction stack turns right for positive `angular.z`, while Nav2 uses the ROS convention (positive turns left). The gate flips the sign (`traction_turn_sign`). Joystick driving does not pass through the gate.
- The manager publishes the robot outline, built from the three chassis transforms, to both Nav2 costmaps, and checks goals against the map with the same outline. The outline extends 0.25 m ahead of the front module (`camera_standoff_m`) so walls stay beyond the arm camera's near clip.
- `cloud_decimator` keeps every 8th pixel of the depth cloud. At full size most clouds were lost in transport and the collision monitor kept stopping the robot.
- `config/nav2_overrides.yaml` holds this package's Nav2 changes on top of the shared `nav2_params.yaml`.
- Stop, cancel, timeout and failure all send a zero command, cancel the Nav2 goal and switch autonomy off, so the joystick works normally again. Moving the joystick past the mux deadband cancels the task.
- Sensor and model deadlines use wall time, so pausing Gazebo fails the task.
- Each task writes `events.jsonl` and up to 1,000 camera frames to `~/.local/state/reseq/traction/TASK_ID/`.

Parameters and their defaults are listed in `reseq_traction_autonomy/parameters.py`.

## Known issues

- Steering responds late when driving forward. The rear modules follow the head's past path, and in Gazebo their bending outweighs the head's own tracks, so after a steering change the robot keeps turning the old way for about one module length. Tight turns swing wide.
- The wheel odometry heading is mirrored: `diff_controller1/odom` reports a left turn when the robot turns right, and the EKF follows it. Only SLAM recovers the true heading. This probably affects the real robot too.
- Nav2 refuses goals where the tail would swing into a wall.
- `simple_course.world` is small for a 1.3 m robot. Straight legs end within 0.1 m of the goal; the turning leg ends about 0.3 m away.
- Nothing has run on the real robot or on the Orin yet.
